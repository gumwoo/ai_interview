# 채점 평가 규칙

M3의 품질 게이트와 M6의 Sonnet 전환에 쓴다. 평가셋은 `eval/grading-cases.json`에 둔다.

## 평가셋

- 정답, 부분정답, 오답, 판단보류 사례를 30건 이상 넣고, 판정은 사용자가 직접 매긴다.
- 쉬운 사례만 넣지 않는다. STT 오인식, 핵심 일부 누락, 그럴듯한 오답, “모르겠어요”를 포함한다.
- 프롬프트 조정용과 확인용을 나눈다. 확인용 사례를 보고 프롬프트를 고치면 과적합이 된다.
- 공개 저장소다. 답변 예시가 약점을 드러낸다면 이 파일을 Git에서 제외한다.

## 실행

- 통과 기준은 실행 전에 정해 적어 둔다. 결과를 보고 기준을 바꾸지 않는다.
- 같은 사례를 3번 돌려 판정이 일정한지 본다. 흔들리는 사례는 따로 기록한다.
- 확인 가능한 항목은 코드로 채점한다. 스키마 유효성, `verdict` 값, 수동 판정과의 일치 여부가 그렇다.
- 해설과 꼬리질문의 품질은 사용자가 판단한다. 모델이 자기 결과를 채점하게 하지 않는다.
- 실제 API를 호출해 크레딧을 쓰므로 자동 테스트에 넣지 않고, 필요할 때만 수동으로 돌린다.

## 기록

- 실행마다 모델, effort, 프롬프트 버전, 사례 버전, 판정 일치 수, 3회 일관성, 토큰, 지연을 남긴다.
- 틀린 사례는 계획서 11.2의 결함 유형(무리한 단정, 모범답변 부정확, 무관한 꼬리질문)으로 분류한다.
- 정확도만 보지 않고 토큰과 지연이 늘었는지도 함께 본다.

## 모델 전환

- Haiku에서 낸 결과를 Sonnet에 그대로 적용하지 않는다. 같은 평가셋을 다시 돌려 비교한 뒤 전환한다.
- effort는 모델마다 기본값이 다르므로 직접 지정하고 기록한다.
